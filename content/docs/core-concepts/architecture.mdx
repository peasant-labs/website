Peasant is a Go CLI application backed by SQLite for storage and a Next.js web dashboard for visual analytics. Everything runs locally on your machine.

## High-Level Architecture

```
┌─────────────────────────────────────────────────┐
│                  CLI (Go)                       │
│  peasant ingest | push | tui | web | ...        │
├─────────────────────────────────────────────────┤
│            Internal Packages                    │
│  ingest │ store │ api │ tui │ providers         │
├─────────────────────────────────────────────────┤
│              SQLite Database                    │
│         ~/.local/share/peasant/peasant.db       │
├─────────────────────────────────────────────────┤
│           Web Dashboard (Next.js)               │
│         localhost:8690                          │
└─────────────────────────────────────────────────┘
```

The CLI is the primary interface. It orchestrates ingestion, manages the database, and can start a web server that serves the dashboard. The TUI provides an alternative terminal-based view into the same data.

## Package Map

Peasant's Go codebase is organized into these key areas:

| Package | Purpose |
|---|---|
| `cmd/peasant` | CLI entry point and command definitions |
| `internal/ingest` | The nine-stage ingestion pipeline |
| `internal/store` | SQLite database access and schema management |
| `internal/api` | HTTP API layer for the web dashboard |
| `internal/tui` | Terminal UI built with a TUI framework |
| `internal/providers` | Provider adapters for Claude Code, OpenCode, etc. |

## Provider System

Peasant uses a provider adapter pattern to support multiple AI coding assistants. Each provider implements a common interface for discovering and parsing session files.

**Currently supported:**

- **Claude Code** — Reads JSONL session files.
- **OpenCode** — Reads JSON session files.

**Schema reserved** (not yet implemented):

- Codex
- Gemini

The provider system uses a factory pattern: the ingest pipeline asks for sessions from each configured provider, and each provider adapter knows how to find and parse its own file format. Adding a new provider means implementing the adapter interface — the pipeline itself does not change.

## Directory Layout

Peasant follows XDG conventions for file storage:

| Path | Contents |
|---|---|
| `~/.config/peasant/config.yaml` | Configuration file (respects `XDG_CONFIG_HOME`) |
| `~/.local/share/peasant/peasant.db` | SQLite database (respects `XDG_DATA_HOME`) |
| `~/.local/share/peasant/peasant-sync/` | Sync data for village push operations |

<Callout type="info">
If you have `XDG_CONFIG_HOME` or `XDG_DATA_HOME` set, Peasant respects those values. The paths above are the defaults when those variables are unset.
</Callout>

## Data Flow

1. **Provider adapters** discover session files on your filesystem.
2. **Ingest pipeline** processes those files through nine stages (see [Ingest Pipeline](/docs/core-concepts/ingest-pipeline)).
3. **SQLite database** stores structured session data, metrics, and indexes.
4. **API layer** serves data from SQLite to the web dashboard.
5. **Web dashboard / TUI** renders analytics for the user.

The database is the single source of truth once data has been ingested. The original session files on disk are never modified.
